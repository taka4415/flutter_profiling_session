01profiling とは

動かして、どこに時間が
消えているかを見る

profiling とは、実際に動いているアプリを計測して、時間とメモリがどこで使われているかを目に見える形にすることです。

読むのではない

コードを眺めて「ここが遅そう」と考えるのは profiling ではありません。動かして、記録を取ります。

推測を潰す道具

「たぶんここ」を「ここだった」に変えるための道具です。当たりを付けるのではなく、確かめます。

特別な準備は要らない

Flutter SDK に最初から DevTools が入っています。追加のライブラリもアカウントも不要です。

01profiling とは

デバッグとは別の仕事

バグパフォーマンス問題
症状動作が間違っている動作は正しい。ただ遅い
再現性条件が揃えば必ず起きる端末・データ量・タイミングで変わる
捕まえ方ブレークポイントで止める止めた瞬間に消える。記録を取るしかない
直ったか動けば分かる測らないと分からない
道具デバッガプロファイラ（DevTools）

パフォーマンス問題は「実行を止めると消える」種類の問題です。だから、止めずに記録する道具が別に用意されています。

01profiling とは

推測するな、計測せよ

なぜ勘が当たらないのか

  • Flutter の 1 フレームは 2 つのスレッドに分かれて動く。遅い原因が Dart のコードとは限らない
  • 同じコードでも、端末・画面サイズ・データ量で結果が変わる
  • 「重そうな見た目のコード」と「実際に時間を食っているコード」は一致しない

よくある空振り

一覧が重い → とりあえず const を付けて回り、ListView.builder に直した。3 時間かけて、体感は変わらなかった。

測ってから直す

DevTools で見たら Raster 側が真っ赤。犯人は行ごとの BackdropFilter だった。1 行消して解決。

DevTools ▸ Performance / CPU Profiler

今日はこれ

増え続けていないか

DevTools ▸ Memory

アプリが太っていないか

ダウンロード率とインストール後の削除率に効く。リリース前にたまに見る。

DevTools ▸ App Size

+α で扱います

3 つは別の道具で測ります。今日はいちばん相談が多い「時間」に絞ります。

02なぜやるのか

「なんか重い」は、
誰にも渡せない

計測する前

「一覧の画面、なんか重いです」

  • どの端末で？ どの操作で？
  • どのくらい重い？
  • 直したとして、直ったとどう言う？

計測したあと

「Pixel 6a / profile モード。一覧を 3 回フリックすると 42 フレームが 16.7ms を超え、最悪 68ms。Raster 側が伸びている」

  • 他の人が同じ手順で再現できる
  • 直った / 直っていないが数字で言える

計測の一番の効能は、速くなることではなく「同じものを見て話せるようになる」ことです。

02なぜやるのか

ジャンク＝ 1 枚のフレームが
予算をはみ出すこと

2 本のグラフ（Performance Overlay の模擬）
Raster UI 予算超過
16.7 ms

60fps 端末が 1 フレームに使える時間。UI と Raster の合計がこれを超えると、その 1 枚は間に合わない。

8.3 ms

120Hz 端末の予算。最近のハイエンドはこちら。予算は半分になる。

間に合わなかったフレームは、直前の絵がもう 1 回表示されます。これが「カクッ」の正体です。

02なぜやるのか

平均ではなく、
最悪値がユーザーの記憶に残る

Aさんのアプリ

平均8.1 ms
中央値7.8 ms
最悪92 ms
16.7ms 超え6 / 300

平均だけ見れば優秀。しかし 6 回カクつくので、ユーザーは「重いアプリ」と言う。

だから、見る数字はこの 3 つ

  • 16.7ms（8.3ms）を超えたフレームの数 — 何回カクついたか
  • 最悪フレームの時間 — どれくらい派手にカクついたか
  • 中央値 — 全体的にじわっと遅いのか、たまに刺さるのか

DevTools の Flutter Frames チャートは、まさにこの「たまに刺さる 1 本」を目で見つけるための道具です。平均値はどこにも出てきません。

031フレームの仕組み

1 枚の絵は、2 つのスレッドを
リレーして作られる

覚えるのは 2 つだけ

UI thread — Dart のコードが動く。build() の中身はここ。ここを塞ぐと全部止まる。

Raster thread — 受け取った Layer tree を GPU で描く。Dart のコードは 1 行も動かない。

Platform スレッドは OS 側とのやりとり、I/O スレッドは画像のデコードなどを担当します。今日はこの 2 つは名前だけ覚えておけば十分です。

031フレームの仕組み

だから、どの道具も
数字を 2 つ出してくる

2 本のグラフ（Performance Overlay の模擬）
Raster UI 予算超過

どちらか一方でも予算を超えたら、
そのフレームはジャンク

合計ではありません。UI と Raster、それぞれが 16.7ms 以内である必要があります。DevTools も、どちらか一方が超えたフレームを赤くします。

Performance Overlay は上下 2 本のグラフ、DevTools の Flutter Frames チャートは 1 本の積み上げバー。見た目は違っても、出している数字は同じ 2 つです。

031フレームの仕組み

赤いのはどちらか。
それだけで、探す場所が決まる

UI thread が赤い

Dart のコードが重い

  • build() の中で毎回、計算・整形・ソートをしている
  • setState() を上の方で呼んでいて、画面全体が作り直されている
  • 大きな JSON のパース、同期のファイル I/O
  • ListView(children: [...]) で全件ぶんを一度に作っている

→ 次に開くのは CPU Profiler

Raster thread が赤い

描くのが重い

  • Opacity / ShaderMask / ColorFilter（内部で saveLayer()）
  • Clip.antiAliasWithSaveLayer での切り抜き
  • BackdropFilter のぼかし、影の重ねすぎ
  • 表示サイズよりずっと大きい画像をそのまま貼っている

→ 次に開くのは More debugging options
（このスイッチだけは debug ビルドで）

Raster 側の原因は、Dart のコードをいくら読んでも見つかりません。「ロジックは何もしていないのに重い」ときは、たいていこちらです。

04進め方

守るのは 3 つだけ

原則 01

profile モードで測る

debug モードの数字は本番と別物です。flutter run --profile で起動します。

debug が遅いのは仕様です。debug の数字で議論しないこと。

原則 02

実機で測る

シミュレータ / エミュレータは計測対象になりません。Dart は速すぎ、GPU の性質も違います。

想定ユーザーが持っている中でいちばん遅い端末を 1 台決めておく。

原則 03

一度に 1 つだけ変える

3 か所直して速くなっても、どれが効いたか分かりません。効かなかった変更を戻せなくなります。

変更 → 計測 → 記録、を 1 セットで。

この 3 つのどれかを破ると、そのあとの作業は全部やり直しになります。まずここだけ守れば、あとは何とかなります。

04進め方

profile モードは、
計測のために用意されている

debugprofilerelease
コンパイルJIT＊1AOT＊2（本番と同じ）AOT＊2
assert・デバッグ用チェックありなしなし
hot reloadできるできないできない
DevTools 接続できるできるできない
速度遅い（仕様）ほぼ本番相当本番
使いどころ開発中計測配布

＊1 JIT = Just-In-Time（実行しながらコンパイル）　＊2 AOT = Ahead-Of-Time（事前にコンパイル済み）

profile ＝ 速さは本番相当のまま、計測だけできるように作られたモード。だから計測は必ずこれで行います。

release は本番そのものですが、計測用の口（VM Service）が閉じているので DevTools がつながりません。

04進め方

同じ輪を、目標に届くまで回す

STEP 4 で複数の変更をまとめないこと。速くなったとき、どれが効いたのか分からなくなります。効かなかった変更はコードに負債として残ります。

04進め方

「同じ操作」を決めてから測る

比べられない測り方

「一覧をなんとなくスクロールして、赤が出たら記録」
→ 次に測るとき、同じ強さでフリックできません。

比べられる測り方

「一覧の先頭から、下方向に 3 回フリック。指を離してから 2 秒待って記録を止める」
→ 誰がやっても、いつやっても、同じ手順です。

操作が手で揺れるのが気になる場合は、記録する区間を長めに取り、フレーム数ではなく超過フレームの割合で比べます。

記録に残す 5 項目

# 一覧スクロールのジャンク
端末      : Pixel 6a（実機）
ビルド    : flutter 3.44.0 / --profile
操作      : 一覧の先頭から下に 3 回フリック
結果      : 16.7ms 超え 42 / 300 フレーム
            worst 68ms（Raster 側）
スクショ  : devtools-before.png

直したあとに同じ 5 行を書けば、それがそのまま「効いた証拠」になります。

04進め方

始める前に、
終わる条件を決めておく

終わらない目標

  • 「速くなるまで」
  • 「サクサクになるまで」
  • 「赤がなるべく減るまで」

どこまでやっても、もう少し速くできてしまいます。

終われる目標

  • 「一覧のスクロールで、16.7ms 超えのフレームを 0 にする」
  • 「worst フレームを 24ms 以下にする」
  • 「タップから画面が出るまでを 400ms 以下にする」

届いたかどうかが、その場で判定できます。

目標は「ゼロ」でなくていい

すべてのフレームを 16.7ms 以内に収めるのは、実機・実データでは簡単ではありません。まずは「一番よく使う画面の、一番よくやる操作」だけを対象にします。

優先順位の付け方

  • 使われる頻度が高い画面から
  • ユーザーが待たされていると気づく操作から
  • 直すコストが小さいものから

目標に届いたら、まだ改善余地があってもそこで止める。最適化は必ずコードの読みにくさと自分の時間を支払うからです。

05ツールの使い方

道具は 4 つ。使う順番が決まっている

まず — どっちが赤い？

01 · Performance Overlay

アプリの画面に直接 2 本のグラフを重ねる。DevTools を開かなくても、その場で分かる。

02 · Performance ビュー

DevTools の本体。フレームごとの記録が残るので、あとから 1 本ずつ調べられる。

次に — どのコード？

03 · Timeline Events

そのフレームの中で何がどれだけ時間を使ったか。Widget 名まで出せる。

UI スレッドが重いときに、メソッド単位まで降りる。Dart のコードだけが対象。

いきなり CPU Profiler を開かないこと。まず「UI と Raster のどちらが赤いか」を見ます。Raster が赤いなら、CPU Profiler には何も写りません。

05ツールの使い方

まず Performance Overlay

出し方

  • flutter run --profile で起動したターミナルで P を押す
  • または DevTools の Performance ビューにあるトグル
  • コードからなら MaterialApp(showPerformanceOverlay: true)

読み方は 3 つだけ

  • 上のグラフ ＝ Raster、下のグラフ ＝ UI
  • 白い横線 ＝ 16ms の予算
  • 線を超えている方が、探すべき側

ここで判断が付けば、DevTools を開かずに済むこともあります。まずはこれ。

05ツールの使い方

DevTools ▸ Performance の地図

  • 1 · Flutter Frames チャート
    操作した分だけ、フレームが 1 本ずつ積まれていきます。
  • 2 · 赤いバー
    予算を超えたフレーム。クリックすると下に詳細が出ます。ここが起点です。
  • 3 · Frame Analysis / Timeline Events
    選んだフレームの中身。まずは Frame Analysis から。
  • 4 · Enhance Tracing / More debugging options
    もっと細かく調べたいときのスイッチ。必要になってから触ります。後者は debug ビルドでのみ有効です。

はじめは「赤いバーを 1 本クリックする」だけで十分です。それ以外のボタンは、必要になってから覚えれば間に合います。

05ツールの使い方

Frame Analysis — 最初に開く場所

赤いバーを選ぶと、DevTools がそのフレームの怪しい場所を文章で教えてくれます。

ここに出るもの

  • そのフレームの UI 時間と Raster 時間
  • 時間を食っていた区間（build / layout / paint / raster）
  • 「この Widget の build が重い」「shader コンパイルが起きた」などのヒント
  • 該当箇所へのリンク

ヒントが出ない、または的外れなこともあります。そのときに初めて Timeline Events を開きます。順番を守ると迷いません。

ここまでで分かること

だいたいの場合、ここで終わります

「UI が 42ms、build が 38ms を占めている」まで分かれば、あとはそのコードを読むだけです。

足りないとき

「どの Widget の build か」まで知りたい → Enhance Tracing（次のスライド）
「どのメソッドか」まで知りたい → CPU Profiler

記録は溜まっていくので、Performance ビューの上部にあるゴミ箱アイコンで一度クリアしてから測り直すと、目的のフレームを見つけやすくなります。

05ツールの使い方

Enhance Tracing で、名前を出す

スイッチTimeline に出るようになるもの
Track Widget Buildsbuild() の呼び出しが、Widget 名つきで出る
Track LayoutsRenderObject の layout が出る。intrinsics を含む
Track PaintsRenderObject の paint が出る

ON にすると、アプリ自体が重くなります

トレースを取ること自体にコストがあるためです。犯人を探すときだけ ON にして、前後比較のときは必ず OFF に戻す。ON のまま測った数字は、比較に使えません。

使いどころ

  • UI スレッドが赤い、しかし Frame Analysis のヒントでは足りない
  • 「どの Widget が毎フレーム作り直されているのか」を知りたい
  • リストの行が想定より多く build されている気がする

手順

  1. Enhance Tracing ▸ Track Widget Builds を ON
  2. 同じ操作をもう一度する
  3. 赤いフレームを選び、Timeline Events タブを開く
  4. 太い帯に Widget 名が入っているので、それを読む
  5. 終わったら OFF に戻す

Track Layouts を ON にすると $runtimeType intrinsics という帯が見えることがあります。これは高さを測るためだけに余計なレイアウト計算が走っているサインで、行の高さを固定すると消えます。

05ツールの使い方

Timeline Events — 横幅が時間

読み方は 2 つだけ

  • 横幅 ＝ かかった時間。細かい帯は無視して、いちばん太い帯を探します
  • 下にたどる。太い帯の下に、さらに太い帯があれば、そちらが本当の原因です

Enhance Tracing を ON にしていれば、帯に Widget 名が入ります。OFF のままだと Build のような大きな括りまでしか分かりません。

自分のコードに Timeline.startSync('名前') を打っておくと、その名前の帯がここに出ます。「この処理が何 ms か知りたい」ときに便利です。（+α で扱います）

05ツールの使い方

消してみて、直るかを見る

Raster が赤いときは、疑わしい描画をまとめて無効化して、直るかどうかを見ます。コードは 1 行も触りません。

スイッチ（More debugging options）OFF にして直ったら
Render Clip layers切り抜きが原因。ClipRRect をやめ borderRadius へ
Render Opacity layers半透明が原因。色の alpha を直接指定するか AnimatedOpacity へ
Render Physical shape layers影・elevation が原因。枚数を減らす

このスイッチは debug ビルド専用です

profile モードでは灰色のまま押せません。切り分けは debug で、時間の数字は profile で測り直す。Raster が何を描くかは debug でも同じなので、犯人探しにはそのまま使えます。

やっていることは二分探索

  1. profile で測って、Raster が赤いと分かっている
  2. --debug で起動し直す
  3. Clip を消す → 直らない → Clip は無罪
  4. Opacity を消す → 直った → 犯人はここ
  5. コードを 1 か所だけ直し、profile に戻して測り直す

OFF にすると見た目は崩れます。それでいいのです。ここで見ているのは見た目ではなく、Raster の時間だけです。

どのスイッチでも直らないときは
画像を疑います。表示サイズよりずっと大きい画像を貼っていないか、cacheWidth / cacheHeight を指定しているか。（+α で扱います）

05ツールの使い方

CPU Profiler — メソッドまで降りる

手順

Record → 重い操作をする → Stop。UI スレッドの Dart コードだけが対象です。

Total time＝呼び出し先も含めた合計。Self time＝そのメソッド自身が使った分。直す価値があるのは Self time が大きいメソッドです。

4 つのタブ

Bottom Up重いメソッドから見る。まずここ
Call Tree重い経路を上から追う
Method TableSelf / Total の一覧。並べ替えできる
Flame ChartCall Tree を絵にしたもの

最初にやること
フィルタで自分のパッケージだけに絞ります。絞らないと Flutter 本体のメソッドで埋まって、自分のコードが見えません。

サンプリングレートは Low 1,000Hz / Medium 4,000Hz（既定）/ High 20,000Hz。細かくするほど正確ですが、アプリ自体が重くなり、記録できる時間も短くなります。既定のままで十分です。

05ツールの使い方

やってみる

cd sample_app
flutter run --profile -d <device-id>

どのデモ画面も、右上のスイッチひとつで「問題のある版」と「改善版」が切り替わります。DevTools を開いたまま前後比較できます。

デモどこに出るか
スクロールのジャンクRaster — Opacity / saveLayer / blur / 影

実演の手順

  1. スイッチ OFF のまま、一覧を勢いよくスクロールする
  2. DevTools ▸ Performance に赤いバーが出る
  3. 赤いバーを 1 本クリック → Frame Analysis を読む
  4. --debug で起動し直し、More debugging options で Opacity / Clip を OFF にして犯人を絞る
    このスイッチは debug 専用。絞れたら profile に戻します
  5. アプリのスイッチを ON にして、同じ操作をもう一度
  6. 赤が消えたことを確認する

端末が速すぎて赤が出ないときは、kTrackCount と kWorkIterations（lib/demo/janky_list_page.dart）を増やしてください。

06クイズ·Q1 / 6
いつもの flutter run で動かしていたら、一覧のスクロールがカクついていました。まず何をしますか？

答え — B

debug モードは JIT で動き、assert やデバッグ用のチェックも走ります。遅いのは仕様です。profile モードで測り直すまで、そのカクつきは本番には存在しないかもしれません。

存在しない問題を追いかけるのが、いちばんもったいない時間の使い方です。

06クイズ·Q2 / 6
DevTools を見たら、Raster の時間だけが予算を超えていました。最初に疑うのはどれですか？

答え — C

Raster スレッドでは、Dart のコードは 1 行も動きません。したがって A も B も無関係です。疑うのは saveLayer() を呼ばせる描画（Opacity / ClipRRect(antiAliasWithSaveLayer) / BackdropFilter）と、影・巨大な画像です。

ここを取り違えると、CPU Profiler を延々と眺めて何も見つからない時間を過ごすことになります。

06クイズ·Q3 / 6
1000 件のリストを ListView(children: items.map(...).toList()) で作りました。何が問題ですか？

答え — B

ListView.builder なら、画面に見えている行だけを作ります。件数が 1000 でも 10000 でも、1 フレームのコストは変わりません。

行の高さが一定なら itemExtent も指定します。高さを測るためのレイアウト計算が丸ごと省けます。

06クイズ·Q4 / 6
「const を付ければ速くなる」— これは正しいですか？

答え — B

const は「この Widget は作り直さなくていい」という印です。UI スレッド側の仕事を減らす効果はありますが、描いたあとの絵が軽くなるわけではありません。

Raster が赤いときに const を付けて回っても、数字は 1ms も動きません。付けること自体は良い習慣ですが、ジャンクの対策としては測ってからです。

06クイズ·Q5 / 6
300 フレーム測ったところ、1 フレームの平均は 8.1ms でした。この画面は大丈夫と言えますか？

答え — B

平均 8.1ms でも、その中に 92ms が 6 回混ざっていれば、ユーザーは「重いアプリ」と言います。

人はスムーズな 294 フレームを覚えず、はみ出した 6 フレームだけを覚えます。見るのは 超過フレーム数 と worst です。

06クイズ·Q6 / 6
UI スレッドが 16.7ms を超えていました。次に開くのはどこですか？

答え — B

順番があります。Frame Analysis のヒント → 足りなければ Enhance Tracing で Widget 名 → それでも足りなければ CPU Profiler でメソッド名。

いきなり CPU Profiler を開くと、Flutter 本体のメソッドが大量に並んで迷子になります。粗いところから順に降りるのがコツです。

仕組みをもう少し

+α時間が余ったら

UI スレッドの中では、
4 つの仕事が順に走る

Build — setState() で dirty になった Element だけを作り直します。画面全部ではありません。重いときは build() の中で計算しているか、setState() を呼ぶ位置が高すぎます。

Layout — 親から子へ制約が下り、子から親へサイズが返ります。ふつうは 1 往復で決まるので速い。intrinsics（高さを測るためだけの追加計算）が走ると遅くなります。

Paint — ここではピクセルは 1 つも塗られません。「どう描くか」を記録するだけです。実際に塗るのは Raster スレッドなので、Opacity や blur の重さはこの帯ではなく Raster 側に出ます。

Timeline Events では、Frame の帯の下にこの順で並びます。どれが太いかで、UI スレッドのどこが重いのかが決まります。

+α時間が余ったら

Timeline の左に並ぶ名前

スレッドのトラック

  • 1.ui — UI スレッド。Dart のコードが動く場所。VsyncProcessCallback / Animator::BeginFrame / BUILD の帯が並びます。まずここ
  • 1.raster — Raster スレッド。Layer tree を GPU コマンドに変えるところ。次にここ
  • 1.io — 画像のデコードなど。出ないこともあります
  • DartWorker — Dart のワーカースレッド。Isolate.run() / compute() に逃がした処理はここに出ます

名前のうしろの数字はスレッド ID です。実行のたびに変わるだけで、意味はありません。

イベントのトラック

  • Frame — 1 枚のフレームの区間。横幅がそのままフレーム時間
  • Frame Request Pending — 「描いてほしい」と要求してから、実際に始まるまでの待ち
  • PipelineItem / PipelineProduce — UI が作った Layer tree を Raster へ受け渡す区間。上が UI 側で作ったもの、下が Raster 側で受け取ったもの
  • PlatformChannel ScheduleResult — MethodChannel でネイティブを呼んだ結果が返ってきた印
  • Process 9116 — プロセス全体の見出し。折りたたみ用で、中身はありません

見るのは 1.ui と 1.raster の 2 本だけで足ります。DartWorker が太くて 1.ui が細ければ、重い処理の追い出しは成功しています。

+α時間が余ったら

Memory — 「閉じたのに減らない」を見つける

Heap Snapshot と Diff の使い方

  1. DevTools ▸ Memory を開く
  2. 問題の画面を開く前にスナップショットを 1 枚撮る
  3. 画面を開いて、閉じる（これを 2〜3 回）
  4. もう 1 枚スナップショットを撮る
  5. Diff タブで 2 枚を比べる

開いて閉じたのにインスタンス数が増えたままのクラスがあれば、誰かがそのオブジェクトを掴んだままです。

よくある原因

  • StreamSubscription を cancel() していない
  • AnimationController / TextEditingController を dispose() していない
  • グローバルな Map や List に入れっぱなし
  • コールバックの中で context や State を掴んでいる

自分のアプリで試す
疑わしい画面を開く前と、開いて閉じたあとにスナップショットを撮って Diff します。増えたままのクラスがあれば、誰かが掴んだままです。

テストの中で dispose 漏れを自動検出する leak_tracker という仕組みもあります。まずは Diff で「増えているか」を見るのが手軽です。

+α時間が余ったら

App Size — 何がアプリを太らせたか

# Android
flutter build apk --analyze-size \
  --target-platform android-arm64

# iOS
flutter build ipa --analyze-size

ビルドが終わると解析用の JSON が出力され、そのまま DevTools の App Size ツールで開けます。

Diff タブで 2 つのビルドを比べられます。「このリリースで 4MB 増えたのは何のせいか」を追うときに使います。

だいたい犯人はこの 3 つ

  • 画像アセット — 4K の PNG がそのまま入っている、@3x だけあれば十分なのに全解像度入れている
  • フォント — 全ウェイト・全字形を同梱している
  • 依存パッケージ — 小さな機能のために大きなライブラリを入れている

サイズはユーザーのダウンロード率とインストール後の削除率に効きます。ただし毎回見るものではなく、リリース前にたまに確認する程度で十分です。

+α時間が余ったら

自分のコードに、名前を付けて測る

同期の区間

import 'dart:developer' as developer;

developer.Timeline.startSync('aggregate');
final result = aggregate(records);
developer.Timeline.finishSync();

非同期の区間

// start と finish が別フレームになるので
// TimelineTask を使う
final task = developer.TimelineTask()
  ..start('aggregate (Isolate.run)');
final result = await Isolate.run(job);
task.finish();

どこに出るのか

DevTools ▸ Performance ▸ Timeline Events に、付けた名前の帯がそのまま出ます。横幅がかかった時間です。

同期は Timeline.startSync、非同期（Isolate.run など）は TimelineTask です。start と finish が別フレームになるときは Task 側を使います。

打ちすぎ注意。1 フレームに何百個も打つと、記録すること自体が重くなって数字が狂います。知りたい区間にだけ、粗く打ちます。

+α時間が余ったら

ユーザーの端末で、測り続ける

import 'package:flutter/scheduler.dart';

SchedulerBinding.instance.addTimingsCallback((timings) {
  for (final t in timings) {
    final build  = t.buildDuration.inMicroseconds / 1000;
    final raster = t.rasterDuration.inMicroseconds / 1000;
    if (build > 16.7 || raster > 16.7) {
      // 分析基盤へ送る（間引くこと）
      reportJank(build, raster);
    }
  }
});

描き終わったフレームの情報が、まとめてコールバックで渡ってきます。buildDuration が UI 側、rasterDuration が Raster 側です。

なぜ必要か

手元で測れるのは自分の端末だけです。3 年前の端末で、通信が遅くて、写真が 5000 枚入っているユーザーの環境は、開発機では再現できません。

送りすぎないこと。全フレームを送ると、送信処理そのものがジャンクの原因になります。閾値を超えたフレームだけ、しかも間引いて送ります。

まずは「超過フレームの割合」だけを画面ごとに集めるところから始めると、改善の効果が数字で見えるようになります。

+α時間が余ったら

「遅い」は 2 種類ある。
待ちと、カクつきは別の病気

待ち — 通信・サーバー

画面は動く。中身が出ない

  • クルクルは回る。スクロールもできる
  • Performance Overlay は緑のまま
  • 犯人は回線、サーバー、直列の API、大きすぎるレスポンス

→ 次に開くのは Network

カクつき — フレーム

指が置いていかれる

  • アニメが飛ぶ。リストが引っかかる
  • Overlay のバーが赤い
  • 犯人は UI / Raster（本編で見たもの）

→ Network は閉じて、Performance に戻る

await http.get(...) は、待っているあいだ UI スレッドを止めません。クルクルが回っているのにカクつくなら、通信ではなくそのあいだに走っている描画や計算です。

よくある取り違え。通信が返った直後に jsonDecode や巨大な setState を同期でやると、「API が遅い」に見えます。固まるのは通信中ではなく、返ってきたあとです。

+α時間が余ったら

通信が遅いかは、消してみれば分かる

切り分けは 3 手

  1. Overlay を出したまま再現する
    緑のまま待つ → ジャンクの道具は閉じてよい
  2. DevTools ▸ Network を見る
    Waiting が長い → サーバーか回線。通信完了の直後に UI が赤い → パースか rebuild
  3. 通信を消して、遅くして、もう一度測る

3 手目の実験
レスポンスをモック（0ms）にしてもカクつく → 通信は無関係。
Charles や Network Link Conditioner で遅くしても Overlay が緑 → 通信。

観察 → 結論

観察結論
Overlay 緑、Network の Waiting が長い回線 or サーバー
Overlay 緑、リクエストが直列に何本もウォーターフォール
通信完了の直後だけ UI が赤いjsonDecode / 巨大な rebuild
モック（0ms）でも赤い通信は無関係
画像だけ遅い。1.io が太いデコード（cacheWidth）

Timeline では、UI が細く空いている区間が長い＝待っている。その直後に BUILD が太い＝返ってきたあとの処理です。

+α時間が余ったら

重い処理は、UI スレッドから追い出す

Before — UI スレッドが止まる

final data = jsonDecode(hugeJson);
final result = aggregate(data);
setState(() => _result = result);

After — 別の isolate へ

import 'dart:isolate';

// job はトップレベル関数にしておく
final result = await Isolate.run(
  () => aggregate(jsonDecode(hugeJson)),
);
setState(() => _result = result);

compute() も同じことをする、もう少し古い書き方です。今から書くなら Isolate.run() で十分です。

使い分けの目安

処理の重さやること
数 msそのままでよい
10〜数十 ms結果をキャッシュする / build から出す
数十 ms 以上Isolate.run() へ

何でも投げればいいわけではありません。isolate との間はデータをコピーして渡すので、その受け渡し自体にコストがあります。小さい処理を投げると、かえって遅くなります。

sample_app のデモ②が、まさにこの Before / After をスイッチで切り替えられるようになっています。

+α時間が余ったら

RepaintBoundary — 使い所を測ってから

何をするものか

囲んだ部分を独立したレイヤーに切り出します。まわりが再描画されても、そこは描き直されなくなります。

効く場面
止まっている複雑な絵（地図・グラフ・長いリストの行）の隣で、何かがずっと動いている。動いているものだけ描き直せばいいのに、全体が描き直されている。

効かない・逆効果な場面
レイヤーを 1 枚増やすたびに GPU メモリを消費します。中身が毎フレーム変わる場所に付けても、描き直しは減りません。「とりあえず全部に付ける」は逆効果です。

入れる前に確認する

import 'package:flutter/rendering.dart';

void main() {
  debugRepaintRainbowEnabled = true;
  runApp(const MyApp());
}

再描画された領域が、フレームごとに色の変わる枠で囲まれます。動いていないのに毎フレーム色が変わっている場所が、候補です。

debug モード専用です。確認が終わったら必ず外してください。

+α時間が余ったら

画像は「表示する大きさ」で読み込む

よくある状態

4000×3000 の写真を、100×100 のサムネイルとして表示している。
→ デコードもメモリも、4000×3000 ぶん払っています。1 枚で約 48MB です。

// 表示する大きさを指定して読み込む
Image.network(
  url,
  cacheWidth: 200,   // 論理px × devicePixelRatio 程度
  width: 100,
  height: 100,
  fit: BoxFit.cover,
)

ImageProvider を直接使う場合は ResizeImage(provider, width: 200) で包みます。

合わせて確認すること

  • アセットの画像が、実際に必要な解像度になっているか
  • リストの行に、毎回別の ImageProvider を作っていないか（キャッシュが効かなくなります）
  • プレースホルダに Opacity を使っていないか（FadeInImage を使う）

Raster が赤いのに、Clip も Opacity も blur も無関係だった — というとき、だいたい画像です。
