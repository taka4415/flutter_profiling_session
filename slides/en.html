01What profiling is

Run the app, and see
where time disappears

Profiling means measuring a running app so you can see where time and memory are actually spent.

Not reading code

Staring at code and thinking “this looks slow” is not profiling. You run it and take a recording.

A tool that kills guesses

It turns “probably here” into “it was here.” You don’t take a guess — you check.

No extra setup

DevTools ships with the Flutter SDK. No extra library, no account.

01What profiling is

Don’t guess, measure

Why hunches miss

  • A Flutter frame runs on two threads. The slow part may not be your Dart code
  • The same code behaves differently by device, screen size, and data volume
  • “Code that looks heavy” and “code that actually costs time” are not the same

A common miss

List feels slow → sprinkle const, switch to ListView.builder. Three hours later, it still feels the same.

Measure, then fix

DevTools showed Raster all red. The culprit was a per-row BackdropFilter. One line deleted, done.

02Why it matters

Before you measure

“The list screen feels kinda slow.”

  • Which device? Which gesture?
  • How slow, exactly?
  • If you ‘fix’ it, how do you say it’s fixed?

After you measure

“Pixel 6a / profile. Three flicks on the list: 42 frames over 16.7ms, worst 68ms. Raster is the long one.”

  • Someone else can reproduce the same steps
  • Fixed / not fixed is a number

The best thing measurement gives you is not speed — it’s being able to look at the same thing and talk.

02Why it matters

Users remember the worst,
not the average

App A

Mean8.1 ms
Median7.8 ms
Worst92 ms
Over 16.7ms6 / 300

The mean looks great. Six hitches later, users call it a “slow app.”

So watch these three numbers

  • Frames over 16.7ms (8.3ms) — how many hitches
  • Worst frame time — how ugly the hitch was
  • Median — generally sluggish, or the occasional spike

The Flutter Frames chart in DevTools exists to spot that one occasional spike. The mean is nowhere on the screen.

03How a frame is built

One picture is a relay
between two threads

Remember just these two

UI thread — Dart runs here. So does build(). Block this and everything stops.

Raster thread — draws the layer tree on the GPU. Not one line of Dart runs here.

The Platform thread talks to the OS. The I/O thread decodes images and similar work. Today, just remember the names.

03How a frame is built

Which one is red?
That alone picks where you look

UI thread is red

Your Dart is expensive

  • build() does compute / format / sort work every time
  • setState() is too high, so the whole screen rebuilds
  • Parsing a huge JSON, or sync file I/O
  • ListView(children: [...]) builds every row up front

→ Next: CPU Profiler

Raster thread is red

Drawing is expensive

  • Opacity / ShaderMask / ColorFilter (they call saveLayer())
  • Clipping with Clip.antiAliasWithSaveLayer
  • BackdropFilter blur, too many shadows
  • An image much larger than its on-screen size

→ Next: More debugging options
(this one only works in a debug build)

Raster-side causes will not show up in Dart, no matter how hard you read. When ‘the logic does nothing’ and it’s still slow, it’s usually this.

04How to work

Only three rules to keep

Rule 01

Measure in profile mode

Debug numbers are not production. Launch with flutter run --profile.

Debug is slow by design. Don’t argue from debug numbers.

Rule 02

Measure on a real device

Simulators and emulators are not a measurement target. Dart is too fast, and the GPU is different.

Pick the slowest device your users actually have and stick with it.

Rule 03

Change one thing at a time

Fix three things and it gets faster — you still don’t know which one worked. You also can’t revert the ones that didn’t.

Change → measure → write it down, as one set.

Break any of these three and everything after is a redo. Keep just this, and the rest will work out.

04How to work

Pick “the same gesture”
before you measure

A measurement you can’t compare

“Scroll the list a bit, record when you see red.”
→ Next time you can’t flick with the same force.

A measurement you can compare

“From the top of the list, three flicks down. Wait 2 seconds after lift-off, then stop.”
→ Anyone, any day: the same steps.

04How to work

Decide the stop condition
before you start

A goal that never ends

  • “Until it’s faster”
  • “Until it feels snappy”
  • “Until there’s less red”

No matter how far you go, you can always go a little further.

A goal you can finish

  • “On list scroll, frames over 16.7ms = 0”
  • “Worst frame ≤ 24ms”
  • “Tap to first paint ≤ 400ms”

You can tell, on the spot, whether you hit it.

The goal does not have to be zero

Keeping every frame under 16.7ms on a real device with real data is hard. Start with the most-used screen and the most-used gesture, only.

How to prioritize

  • Most-used screens first
  • Gestures where users notice they’re waiting
  • Cheap fixes first

When you hit the goal, stop — even if more is possible. Optimization always costs readability and your time.

05Using the tools

Frame Analysis — open this first

Select a red bar and DevTools tells you, in words, what’s suspicious in that frame.

What shows up here

  • UI time and Raster time for that frame
  • Which stretch ate the time (build / layout / paint / raster)
  • Hints like “this widget’s build is expensive” or “a shader compiled”
  • Links to the matching spots

Sometimes there’s no hint, or it’s off. That’s when you open Timeline Events. Keep the order and you won’t get lost.

What you already know here

Most of the time, you stop here

If you know “UI is 42ms, build ate 38ms,” you just go read that code.

When it isn’t enough

Want the widget name? → Enhance Tracing (next)
Want the method? → CPU Profiler

Recordings pile up. Hit the trash icon at the top of Performance, then measure again — the frame you care about is easier to find.

Only two ways to read it

  • Width = time spent. Ignore thin bars. Find the widest one
  • Walk down. If a wide bar has an even wider child, that’s the real cause

05Using the tools

Turn it off and see if it recovers

When Raster is red, disable a whole class of drawing and see if it recovers. You don’t touch a line of code.

Switch (More debugging options)If OFF fixes it
Render Clip layersClipping. Drop ClipRRect, use borderRadius
Render Opacity layersOpacity. Set color alpha, or use AnimatedOpacity
Render Physical shape layersShadows / elevation. Use fewer of them

These switches are debug-only

In profile they’re gray and you can’t click them. Isolate in debug; remeasure times in profile. What Raster draws is the same in debug, so hunting still works.

What you’re doing is a binary search

  1. You already measured in profile: Raster is red
  2. Relaunch with --debug
  3. Kill clips → still broken → clips are innocent
  4. Kill opacity → recovers → that’s the culprit
  5. Fix one place in code, go back to profile, measure again

OFF will make it look broken. That’s fine. You’re watching Raster time, not looks.

If no switch fixes it
Suspect images. Are you showing a much larger image than the on-screen size? Did you set cacheWidth / cacheHeight? (covered in Extra)

06Quiz·Q1 / 6
You launched with plain flutter run and list scroll hitches. What do you do first?

Answer — B

Debug runs JIT, plus asserts and debug checks. Slow is by design. Until you remeasure in profile, that hitch may not exist in production.

Chasing a problem that isn’t there is the most expensive way to spend time.

06Quiz·Q2 / 6
DevTools shows only Raster time over budget. What do you suspect first?

Answer — C

On the Raster thread, not one line of Dart runs. A and B are irrelevant. Suspect drawing that forces saveLayer() (Opacity / ClipRRect(antiAliasWithSaveLayer) / BackdropFilter), plus shadows and huge images.

Mix this up and you’ll stare at CPU Profiler forever and find nothing.

06Quiz·Q3 / 6
You built a 1000-row list with ListView(children: items.map(...).toList()). What’s the problem?

Answer — B

ListView.builder builds only the rows on screen. 1000 or 10,000 rows — the cost per frame stays the same.

If row height is fixed, also set itemExtent. The extra layout just to measure height goes away.

06Quiz·Q4 / 6
“Adding const makes it faster.” Is that true?

Answer — B

const means “don’t rebuild this widget.” It can cut UI-thread work, but it does not make the painted picture cheaper.

Sprinkle const while Raster is red and the number won’t move 1ms. Adding it is a good habit — as a jank fix, measure first.

06Quiz·Q5 / 6
You measured 300 frames. Mean frame time is 8.1ms. Can you say this screen is fine?

Answer — B

A mean of 8.1ms can still hide six 92ms frames. Users will call it a slow app.

People don’t remember 294 smooth frames — only the 6 that overshot. Watch over-budget count and worst.

06Quiz·Q6 / 6
The UI thread went over 16.7ms. What do you open next?

Answer — B

There’s an order. Frame Analysis hints → if that’s not enough, Enhance Tracing for widget names → then CPU Profiler for methods.

Open CPU Profiler first and Flutter’s own methods bury you. Walk down from the coarse view.

ExtraIf you have time

Inside the UI thread,
four jobs run in order

Build — rebuilds only Elements marked dirty by setState(). Not the whole screen. When it’s slow, you’re computing inside build(), or setState() is too high.

Layout — constraints go parent → child, sizes come back child → parent. Usually one round trip, so it’s fast. intrinsics (extra work just to measure height) makes it slow.

Paint — not one pixel is filled here. It only records how to draw. Raster does the filling, so Opacity and blur cost shows up on Raster, not in this bar.

In Timeline Events these sit under the Frame bar, in this order. Whichever is widest tells you where the UI thread is heavy.

ExtraIf you have time

Names on the left of Timeline

Thread tracks

  • 1.ui — the UI thread. Where Dart runs. You’ll see VsyncProcessCallback / Animator::BeginFrame / BUILD. Start here
  • 1.raster — the Raster thread. Turns the layer tree into GPU commands. Then here
  • 1.io — image decode and similar. Sometimes missing
  • DartWorker — Dart worker threads. Work you sent to Isolate.run() / compute() lands here

The number after the name is a thread id. It changes every run and means nothing.

Event tracks

  • Frame — one frame’s span. Width is the frame time
  • Frame Request Pending — wait from “please draw” until work actually starts
  • PipelineItem / PipelineProduce — handing the layer tree from UI to Raster. Top is what UI built, bottom is what Raster received
  • PlatformChannel ScheduleResult — a native MethodChannel result came back
  • Process 9116 — a process-level heading. For folding; nothing inside

You only need 1.ui and 1.raster. If DartWorker is wide and 1.ui is thin, moving the heavy work off succeeded.

ExtraIf you have time

Memory — find “I closed it, it never shrinks”

How to use Heap Snapshot and Diff

  1. Open DevTools ▸ Memory
  2. Take one snapshot before opening the suspect screen
  3. Open the screen, close it (repeat 2–3 times)
  4. Take another snapshot
  5. Compare the two in the Diff tab

If a class’s instance count stays up after open-and-close, someone is still holding those objects.

Usual causes

  • A StreamSubscription you never cancel()
  • An AnimationController / TextEditingController you never dispose()
  • Stuff left in a global Map or List
  • A callback holding context or a State

Try it in sample_app demo ③
Each detail screen allocates 2MB and subscribes to a global StreamController without cancel(). Hit “open and close 10 times,” then Diff: ten DetailPayloads (~20MB) stay and never come back.

There’s also leak_tracker, which can catch missed disposes in tests. Easiest first step: Diff, and ask “did it grow?”

  --target-platform android-arm64

When the build finishes you get an analysis JSON. Open it in DevTools ▸ App Size.

The Diff tab compares two builds. Use it for “what added 4MB in this release?”

Usually one of these three

  • Image assets — a 4K PNG shipped as-is, or every density when @3x would do
  • Fonts — every weight and every glyph bundled
  • Dependencies — a huge library for a tiny feature

Size hits download rate and post-install uninstalls. You don’t need it every time — an occasional pre-release check is enough.

ExtraIf you have time

Keep measuring on users’ devices

import 'package:flutter/scheduler.dart';

SchedulerBinding.instance.addTimingsCallback((timings) {
  for (final t in timings) {
    final build  = t.buildDuration.inMicroseconds / 1000;
    final raster = t.rasterDuration.inMicroseconds / 1000;
    if (build > 16.7 || raster > 16.7) {
      // send to analytics (sample it)
      reportJank(build, raster);
    }
  }
});

Finished-frame timings arrive in a batch callback. buildDuration is UI, rasterDuration is Raster.

Why you need it

At your desk you can only measure your own device. A three-year-old phone, a slow network, and 5000 photos — you won’t reproduce that on a dev machine.

Don’t send everything. Shipping every frame makes the send itself a source of jank. Send only frames over the threshold, and sample those.

Start by collecting just “share of over-budget frames” per screen. Then you can see whether a fix moved the number.

ExtraIf you have time

“Slow” is two diseases.
Waiting and jank are not the same

Waiting — network / server

The UI moves. Content doesn’t show

  • The spinner spins. You can still scroll
  • Performance Overlay stays green
  • Culprit: link, server, serial APIs, a huge response

→ Next: Network

Jank — frames

Your finger leaves the UI behind

  • Animations skip. The list catches
  • Overlay bars go red
  • Culprit: UI / Raster (what the main talk covered)

→ Close Network, go back to Performance

await http.get(...) does not block the UI thread while it waits. If it hitches while the spinner spins, it isn’t the request — it’s drawing or compute running in the meantime.

A common mix-up. Sync jsonDecode or a huge setState right after the response looks like “the API is slow.” The freeze is after it returns, not during the request.

ExtraIf you have time

Is the network slow? Turn it off and see

Three moves to isolate it

  1. Reproduce with Overlay on
    You wait, and it stays green → close the jank tools
  2. Look at DevTools ▸ Network
    Long Waiting → server or link. UI goes red right after completion → parse or rebuild
  3. Delete the network, slow it down, measure again

Experiment #3
Mock the response at 0ms and it still hitches → not the network.
Slow it with Charles or Network Link Conditioner and Overlay stays green → the network.

Observation → conclusion

ObservationConclusion
Overlay green, long Waiting in NetworkLink or server
Overlay green, many serial requestsWaterfall
UI red only right after the responsejsonDecode / a huge rebuild
Still red with a 0ms mockNot the network
Only images are slow. 1.io is wideDecode (cacheWidth)

In Timeline, a long thin empty UI span = waiting. A wide BUILD right after = work after the response.

ExtraIf you have time

Move heavy work off the UI thread

Before — the UI thread stops

final data = jsonDecode(hugeJson);
final result = aggregate(data);
setState(() => _result = result);

After — another isolate

import 'dart:isolate';

// keep job as a top-level function
final result = await Isolate.run(
  () => aggregate(jsonDecode(hugeJson)),
);
setState(() => _result = result);

compute() does the same thing, in an older style. For new code, Isolate.run() is enough.

A rough split

How heavyWhat to do
A few msLeave it
10–tens of msCache the result / take it out of build
Tens of ms or moreSend it to Isolate.run()

Don’t toss everything over. Data is copied across the isolate boundary, and that copy costs. Tiny work gets slower, not faster.

Demo ② in sample_app is this Before / After, flipped with one switch.

ExtraIf you have time

RepaintBoundary — measure the spot first

What it does

It cuts the wrapped subtree into its own layer. Neighbors can repaint without redrawing it.

When it helps
A still, complex picture (map, chart, a long list row) sits next to something that keeps moving. You only need to redraw the moving part — but everything redraws.

When it doesn’t — or backfires
Each extra layer costs GPU memory. Wrap something that changes every frame and you don’t save any redraws. “Just put it everywhere” backfires.

Check before you add one

import 'package:flutter/rendering.dart';

void main() {
  debugRepaintRainbowEnabled = true;
  runApp(const MyApp());
}

Repainted regions get a border that changes color every frame. Places that aren’t moving but still change color every frame are candidates.

Debug-only. Take it out when you’re done checking.

ExtraIf you have time

Decode images at the size you show

A common state

A 4000×3000 photo shown as a 100×100 thumb.
→ Decode and memory still pay for 4000×3000. About 48MB per image.

// decode at the size you display
Image.network(
  url,
  cacheWidth: 200,   // logical px × devicePixelRatio-ish
  width: 100,
  height: 100,
  fit: BoxFit.cover,
)

If you use an ImageProvider directly, wrap it in ResizeImage(provider, width: 200).

Also check

  • Asset images are actually the resolution you need
  • List rows aren’t creating a new ImageProvider every time (that kills the cache)
  • The placeholder isn’t using Opacity (use FadeInImage)

Raster is red, and Clip / Opacity / blur are innocent — it’s usually images.

ExtraIf you have time

Most articles on the web
are already outdated

Performance write-ups are full of pieces from before Impeller (the Skia era). Copy them as-is and you’ll apply fixes that no longer apply.

Signs the article is old

  • --purge-persistent-cache
  • SkSL warm-up / shader compilation jank
  • “The first animation always janks”
  • Precompile your shaders

If you see these, the article’s premise is not today’s. Since Impeller became the default, shaders stopped being the usual first-frame culprit.

What to do now

  • Check the date first. Treat anything before 2023 as suspect
  • Read the official docs first
  • Jank only on first play → look at image decode and first-run work

When in doubt, check the date on the official page. The links on the next slide are official-only.
